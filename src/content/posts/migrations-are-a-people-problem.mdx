We spent four months moving billing off the monolith. The schema work took two weeks. Everything after that was conversations.

The plan looked clean on the whiteboard: stand up the new service, dual-write, backfill, cut over, delete the old tables. What the whiteboard didn't show was the eleven other teams reading from those tables directly[^1], none of whom had been in the room, most of whom found out from a deprecation notice in a channel they'd muted.

So the interesting artifact of the project wasn't the new service. It was the inventory we built along the way — every consumer, what it read, and who to call when it broke.

## Finding the readers

Query logs told us more than any architecture diagram. A day of samples, grouped by client and table, gave us the real dependency graph:

```go
// consumers groups a day of query samples by client, so a migration
// plan can start from who actually reads a table.
func consumers(rows []Sample) map[string]*Client {
    seen := make(map[string]*Client, 64)
    for _, r := range rows {
        if r.Table != "billing_invoices" {
            continue
        }
        c, ok := seen[r.AppName]
        if !ok {
            c = &Client{Name: r.AppName, Owner: "unknown"}
            seen[r.AppName] = c
        }
        c.Reads++
        c.Columns.Add(r.Columns...)
    }
    return seen
}
```

Sorted by read count, that map is a call list. The top four accounted for most of the traffic; the long tail was where the surprises lived[^2].

## What I'd do differently

Build the inventory first, before the design doc. It changes the plan, and it tells you how long the project really is — which is however long it takes eleven teams to find room in their sprints.

The schema was never the hard part. It never is.

[^1]: Nine of them via a read replica nobody owned. We found the last two by turning the credentials off and waiting.
[^2]: One consumer was a quarterly finance report run from someone's laptop. It would have failed silently in October.
